Your suite is green. How much of it still ran?

We ran this audit, uninvited and read-only, on a well-maintained public open-source project — the reference JSON Schema validator for Python, whose suite runs 8,512 tests and passes clean. We deleted its entire enumerated conformance corpus — 91.8% of the executed cases — and the suite reported an unqualified green: “701 passed”, exit 0. Then we flipped a single expected value in one surviving case, and the same suite went red — exit 1, exactly 1 failure, naming exactly that case. Every test that runs is judged honestly; nothing notices whether what runs is still there. That is the shape this audit finds: your green certifies what was evaluated, and says nothing about how much was.

What the audit is

Measure whether your CI's green means anything. A test suite asserts that everything it ran was acceptable; it is silent about how much it ran — and those are different properties, independently variable, of which only the first ever appears in the summary line. This audit measures the second one: for each component of your checking layer, we narrow the input it enumerates — fixtures, golden files, generated cases, discovered tests — re-run it, and watch whether the verdict moves.

Every finding ships with a kill-control: a deliberate single-value corruption the same component must catch, proving the component is alive and the blindness is specific — not an artifact of a broken harness or a broken measurement. Both directions, always: no blindness verdict without its red proof, and no green trusted until it has been shown able to go red.

The kill-control, in a copy of the 80%-pruned suite: one expectation flipped (tests/draft7/additionalItems.json, "valid": true → false) → exit 1, 2206 passed, and the single failure is exactly the mutated case, TestDraft7::test_additionalItems_additionalItems_as_schema_additional_items_match_schema. Every surviving case is honestly adjudicated — which is what makes the green at −91.8% a finding about enumeration, not about correctness. The boundary is exact, and instructive: about a dozen optional files are opened by literal path and are loud when one is removed (collection error before any test runs, exit 2) — that is what a defended enumeration looks like, and the 417 glob-swept files have no equivalent guard.

What this is not

This is not mutation testing, and a good mutation score does not answer it. Mutation testing perturbs code semantics over the set of tests that execute; this audit perturbs the enumeration that decides what executes. The surfaces are disjoint: a suite can carry a perfect mutation score over its surviving cases and still stay green after losing most of them, because every adequacy measure is computed over the tests that ran. Coverage does not close the gap either — data-driven cases share code paths, so a fixture corpus can shrink drastically while line and branch coverage barely move.

Scope, stated

The audited project comes out clean where it was tested: its adjudication of what runs is honest — proven, by the kill-control above — and the finding is confined to the layer that decides what runs. The exhibit measurement was made respectfully, read-only, on a local clone; the absence of an enumeration census is the industry default, not that project's defect, which is exactly why it is worth measuring.
