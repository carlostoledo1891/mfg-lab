Auditing benchmarks from the outside

A leaderboard reports pass or fail. Can an outsider check the passes — for free, from public data, with a witness for every flag? Two probes, two benchmarks, and one honest pattern: where the free data reaches, the benchmarks turn out well-built; where the teeth are, the data is gated.

What this is — and is not

A screen, not a verdict. Patch-shape divergence is not evidence of error or gaming, and a test that rejects a trivial answer is a benchmark working. No model is named as cheating. Both benchmarks are credited. The value here is a validated instrument and an honest map of what the free data can and cannot support. Every number is a dated record (2026-08-22); re-run the two scripts below to refresh.

Probe 1 — SWE-bench Verified: the coverage wall

When a model is marked resolved, how far does its patch diverge in shape — files, lines, hunks — from the human gold fix? From the git-tracked data alone: 134 submissions carry results.json, but only 13 carry patch_stats.json, and all 13 are from 2023–2024. Not one current model is reachable for free — the actual patches are behind the project's S3.

Among the six 2024 submissions with a readable sample (≥100 resolved), the share of resolved patches that diverge extremely from the gold fix (3× its files, 5× its size, or near-empty where the gold is substantial): appmap-navie/gpt-4o 16.8%, SWE-agent/gpt-4 14.3%, Amazon-Q 12.9% and 10.2%, AutoCodeRover 7.8%, Factory Droid 4.9%. A real but modest signal — on stale models, and shape is not correctness.

Per-instance attribution is impossible here, and that is a proof, not an assumption. The gold patch for a fixed instance is constant, so if the stats were ordered like the resolved list, the same instance would report the same gold shape across submissions. It does not — 664 conflicts — which proves the two arrays are ordered differently. Aggregate divergence survives; named-instance callouts do not, and were dropped.

Probe 2 — BigCodeBench: the pipeline works, the benchmark is strong

Here the data is reachable: tasks as public JSON, per-model generations as a 161 MB GitHub release, a local Python oracle. So the full outside-auditor runs — assemble the solution, run the benchmark's own test, verdict by exit code (a timeout is INOPERATIVE, never a pass). The cheapest false-pass question: does a task's test wave through a constant return?

Red control first (a screen that cannot go red proves nothing): against the real test, return 1.0 is rejected (FAIL, caught); against a deliberately weakened test it sails through (PASS, flagged); the canonical solution stays green. The detector is not blind.

Pointed at real tasks: 0 of the 7 stdlib-only tasks accepted any trivial solution (return 0 / None / 1.0 / [] / "" / {}). BigCodeBench's tests are strong — exactly what you expect of a benchmark built to be the strict successor to HumanEval. Low yield for the weak-test angle; the pipeline, though, reaches current models and is ready to scale.

What the reconnaissance found

The same shape twice, and it is the useful result: the reachable, free audits keep finding the benchmarks well-built. SWE-bench's free layer cannot touch a current model; BigCodeBench's tests reject the cheap exploits. The teeth for an outside audit live where the data is gated — SWE-bench's actual patches (a free account, real effort), whose per-instance tests are weaker and whose patches are known to be gameable. The instrument is built, validated, and current-model-capable on BigCodeBench; the next move is the gated pull, not another free screen.

  • Higher-yield angle, documented not yet run: reproduction and flakiness of published passes — re-run each solution K times and flag those that do not hold up. On a 139-library benchmark that is where fragility hides.
  • The prize stays SWE-bench: the same pipeline, the repo's own test harness as oracle, once the patches are pulled.

Run it yourself

Both scripts ship here. The SWE screen needs only network; the BigCodeBench auditor needs Python and, to audit real downloaded generations at scale, a sandbox — never exec untrusted model code on a bare machine.

git clone --depth 1 https://github.com/carlostoledo1891/mfg-lab
cd mfg-lab/research/methods/audits
node swe_patch_screen.js         # the 13/134 coverage wall + 664-conflict proof
python3 bigcodebench_audit.py    # the red control, then 0-of-7 on the sample
